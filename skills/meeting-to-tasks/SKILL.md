# Meeting to tasks

Turn a messy meeting record into a short list of commitments people will actually act on. The output must be trustworthy: every action item is backed by a quote from the source, owners are real attendees, and dates are concrete.

## Workflow

### 1. Establish context

Find or ask for: meeting title, **meeting date** (needed to resolve "next Friday"), attendees, and the target tracker if the user wants an export. If the date is missing and cannot be inferred, ask once; otherwise state the date you assumed at the top of the summary.

### 2. Extract, with evidence

Read the full record and classify each relevant statement:

- **Decision** - something agreed ("we'll go with Stripe"). Not a task.
- **Action item** - a specific person committed, or was asked and agreed, to do something.
- **Open question** - raised but not resolved, or needs someone outside the meeting.
- Ignore ideas that nobody took on, small talk and status updates with no follow-up.

For each action item record the shortest verbatim `source_quote` that proves it. If you cannot point to a quote, it is not an action item - put it under open questions instead. This is the main defence against inventing work.

### 3. Fill the fields

Follow `references/output-schema.md` exactly. The rules that matter most:

- **title**: starts with a verb, under 80 characters, understandable without the meeting ("Send revised SOW to Acme", not "SOW").
- **owner**: an attendee's name as written in the attendee list. If nobody took it, use `"Unassigned"` - never guess.
- **due_date**: ISO `YYYY-MM-DD`, resolved against the meeting date. Set `due_basis` to `explicit` (a date or day was said), `inferred` (derived from a stated dependency or deadline - explain in `description`) or `none` (`due_date: null`).
- **priority**: `high` = blocks a deadline, a customer or other people's work; `medium` = needed this cycle; `low` = nice to have. Briefly justify high priority in the description.
- **depends_on**: ids of action items that must finish first.

### 4. Write the files

Produce three artifacts (save them when files can be written, otherwise show them in full):

1. `tasks.json` - the structured data.
2. `tasks.md` - the human recap: one-paragraph summary, decisions, action items table (ID, task, owner, due, priority), open questions. Keep it skimmable; it is often pasted into Slack or email.
3. Tracker CSV - generated by the script, never written by hand.

### 5. Validate and export with the script

```bash
python scripts/tasks_tool.py validate tasks.json --transcript transcript.txt
python scripts/tasks_tool.py export tasks.json --format jira -o tasks-jira.csv
```

`validate` checks the schema, ids, owners against attendees, dates, dependencies and - with `--transcript` - that every `source_quote` really appears in the source (whitespace and case are normalised). Fix every error and re-run until it passes; treat warnings as things to double-check. `export` supports `jira`, `asana`, `notion` and `generic`; see `references/output-schema.md` for the columns and import tips for each tool.

If Python is unavailable, run the same checks by hand against the schema and say that the script was not run.

### 6. Report back

Show the `tasks.md` content, mention the validation result, list the files produced, and call out anything uncertain: unassigned items, inferred dates, and attendees mentioned in the record but missing from the attendee list.
